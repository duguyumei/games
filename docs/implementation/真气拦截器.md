# 真气拦截器

> 状态：已实现，未接入运转动作
> 相关设计：[内功](../game-design/06-内功.md)、[功法调度](../game-design/02-功法调度.md)

内功、功法、真气状态想影响一个战斗动作时，靠这套机制介入。动作本身不认识任何具体内功 —— 影响者自己登记到注册表，动作执行时查表。

框架自带另一套拦截器（`scripts/action_interceptors/`），服务攻击这类有明确受击者的动作。本文这套服务真气动作，两套并行，最终目标是前者迁移过来后删除。

## 1. 为什么不用框架那套

框架用「发起者 / 承受者」两个位置定位效果：

```text
我打敌人 → 发起者 = 我，承受者 = 敌人
  我的「力量+3」   挂发起者位置，modifies_parent = true
  敌人的「易伤」   挂承受者位置，modifies_parent = false
```

一个拦截器要生效，得同时满足两个条件：挂在这两个位置之一，且 `modifies_parent` 与所在位置对得上。

问题出在**作用于自己的动作**上 —— 运转、抽气、回血、加护甲。这类动作没有承受者，承受者位置是空的。于是「敌方运转时反震 3 点」这个效果无处可挂：挂发起者不对（发起者是敌人，效果是我的），挂承受者查不到（位置为空）。

绕过它的两种办法都有代价：承受者填对方是语义谎言（运转并不作用于敌人）；拆成「本方链 + 对方链」两条链则让优先级只在链内有效 —— 敌方「运转无效」优先级 1000 排不到我方「气力+2」优先级 100 前面。

## 2. 这套怎么做

**换查找维度。** 注册表的 key 从战斗者改成动作类型，每条记录带上 `owner`（这个效果属于谁）。

```text
{
  "res://.../ActionCirculateQi.gd": [
    {id: "气力+2", owner: 玩家, phase: BEFORE, ...},
    {id: "反震3点", owner: 玩家, phase: AFTER,  ...},
    {id: "运转无效", owner: 敌人, phase: BEFORE, ...},
  ]
}
```

判断一个拦截器是否生效只剩一个比较：

```text
owner == 动作发起者  →  「自己发动」
owner != 动作发起者  →  「对方发动」
```

配置里用 `watches_opponent` 声明关心哪一种。`modifies_parent` 那个维度不需要了。

**于是敌我拦截器天然在同一个数组里**，排序后优先级跨阵营有效 —— 这是这套相对框架那套唯一的功能性收获。

## 3. 组成

| 文件 | 职责 |
|---|---|
| `data/readonly/QiInterceptorData.gd` | 固定配置：脚本路径、动作白名单、关心谁发动、时机、优先级 |
| `scripts/qi_interceptors/BaseQiInterceptor.gd` | 拦截器基类，子类重写 `process_qi_interception()` |
| `scripts/qi_interceptors/QiInterceptorRegistration.gd` | 一条注册记录，带 `owner` 与来源信息 |
| `scripts/qi_interceptors/QiInterceptorRegistry.gd` | 注册表，key 是动作路径 |
| `scripts/qi_interceptors/QiInterceptorResolver.gd` | 查找、排序、执行一条链 |

注册表实例挂在 `ActionHandler.qi_interceptors`。

## 4. 一次拦截的完整流程

```text
装备内功
  └─ Player.register_neigong_interceptors()          Player.gd:227
       └─ ActionHandler.qi_interceptors.register(玩家, 拦截器id, "neigong", 内功uid, 装备顺序)
            └─ 读配置的动作白名单，在每个动作路径下各存一条记录

动作执行
  └─ 动作调 _intercept_qi_action()                    BaseAction.gd
       └─ QiInterceptorResolver.run()
            ├─ _collect()
            │    ├─ 拿动作路径查表，一次拿到全部候选
            │    ├─ 过滤：阶段不符的跳过
            │    ├─ 过滤：watches_opponent 与「owner == 发起者」对不上的跳过
            │    └─ 排序：优先级降序 → source_order → registration_order
            └─ 逐个 load().new() 并调 process_qi_interception()
                 ├─ CONTINUE  继续下一个
                 ├─ STOPPED   动作照常执行，后续拦截器不跑
                 └─ REJECTED  动作不执行（AFTER 阶段按 STOPPED 处理）
```

## 5. 两个时机

`qi_interceptor_phase` 声明拦截器在动作执行前还是执行后生效。前后各跑一条独立的链、各自排序。

```gdscript
# 动作里的用法
var resolver := _intercept_qi_action()                    # BEFORE
if resolver == null:
    return                                                 # 被拒绝，动作不执行
var to_zone: int = resolver.get_shadowed_value("to_zone", -1)
...执行动作...
_intercept_qi_action(QiInterceptorData.PHASES.AFTER)      # AFTER
```

`BEFORE` 能改参数、能拒绝动作。`AFTER` 时动作已执行完，只能读结果与追加效果 —— 返回 `REJECTED` 无意义，会被当作 `STOPPED`。

## 6. 配置与中文描述一字对应

| 效果 | `watches_opponent` | `phase` |
|---|---|---|
| 运转时气力 +2 | `false` | `BEFORE` |
| 敌方运转无效 | `true` | `BEFORE` |
| 运转后气力 -1 | `false` | `AFTER` |
| 敌方运转后反震 3 点 | `true` | `AFTER` |

配置在代码里构造，不是 `.tres`：`GlobalProdDataGenerator.add_qi_interceptors()`。**测试环境是另一份名单**，新增拦截器必须同时在 `GlobalTestDataGenerator.add_test_qi_interceptors()` 登记，否则测试环境不生效。

## 7. 数值不写在脚本里

拦截器脚本是通用的，数值从来源实例读：

```gdscript
var neigong_data: NeigongData = resolver.get_source_instance()
var amount: int = neigong_data.neigong_interceptor_values.get("momentum_amount", 0)
```

所以「运转时气力+1」和「运转时气力+2」共用同一个脚本，差异全在 `NeigongData.neigong_interceptor_values` 里。参考实现：`scripts/qi_interceptors/InterceptorQiMomentumOnCirculate.gd`。

## 8. 拦截器的三条硬规则

**不能存状态。** `extends Resource`，每次拦截都 `load().new()` 新建实例，挂在拦截器上的属性存不住。所有状态从 `resolver` 或来源实例读。

**preview 时不能有副作用。** 界面预览「这次运转会变成什么结果」时会跑同一条链。改实例、发信号、衰减层数这类操作要在方法开头短路：

```gdscript
if preview_mode:
    return ACCEPTANCES.CONTINUE
```

预览期间 `ActionHandler.add_actions()` 会自动丢弃入队请求，但直接改数据不受保护。

**preview 时不能返回 `REJECTED`。** 否则预览显示的数值与实际打出的不一致。

## 9. 清理时机

| 时机 | 做什么 |
|---|---|
| 内功配装变化 | `unregister_by_source_kind(玩家, "neigong")` 后整体重建（幂等） |
| 战斗结束 | `unregister_except_owner(Global.get_player())` —— 只清敌方 |
| 一局结束 | `clear_all()` |

战斗结束**不能**整表清空。玩家的内功注册由 `Player.reset_player()` 建立，而那个方法只在一局开始时调用一次（`_on_run_started`），不是每场战斗 —— 整表清会让玩家内功从第二场战斗起全部失效。

归属者已被 `queue_free` 的记录在清理和查找时都会跳过（`is_instance_valid` 检查）。敌人正是在 `combat_ended` 时销毁的，与清理挂同一个信号，回调顺序不确定。

## 10. 与框架那套的已知差异

**不支持 `forced_interceptor_ids`**（未注册也强制生效）。真气效果一律通过注册表生效，没有强制注入的场景。

**`ignore_all_interceptors` 读动作原始值**而非 shadow 值。`_collect()` 在链开始前调用，此时还没有拦截器写过 shadow，两者结果相同。

**`custom_key_names` 已支持**，与框架行为一致 —— 一张卡上有两个同类动作时靠它区分参数。

**一次注册共用一个 `registration_order`**（同一拦截器在多个动作路径下的记录序号相同）。不影响排序稳定性，因为每次查找只针对一个动作路径。

# 架构

> 状态：初稿
> 前置：[游戏概述](../game-design/00-游戏概述.md)
> 相关：[真气拦截器](./真气拦截器.md)

本文定义分层结构与模块边界。目的是让「一个效果该写在哪里」有唯一答案。

## 1. 现状

2026-08-31 删除旧框架后，代码只剩两层：

```text
data/
  prototype/   QiData, NeigongData          配置与实例数据
  mutable/     BattleQiState, QiStateEntry, QiReshape
  readonly/    QiEnums, QiInterceptorData
scripts/
  qi_interceptors/   拦截器体系（5 个类）
  qi_states/         StateHandler, QiActionContext
  actions/           BaseAction, ActionSource（新写，未验证）
```

**没有**：战斗流程、动作队列、战斗者、UI、全局单例。

删除旧框架的原因：它用「发起者 / 承受者」定位效果，是照攻击设计的。真气运转作用于自己，没有承受者，「敌方运转时反震」无处可挂。绕过它的成本高于重写。

## 2. 分层

四层，依赖只能向下。

```text
┌─────────────────────────────────────┐
│ 表现层  scenes/ + ui/               │  场景、控件、动画
│         只读状态，只发意图信号        │
├─────────────────────────────────────┤
│ 流程层  battle/ + run/              │  回合推进、行动组、探索节点
│         创建并执行动作                │
├─────────────────────────────────────┤
│ 动作层  actions/ + qi_interceptors/ │  一次状态变更 + 效果介入
│         唯一有权修改数据的地方        │
├─────────────────────────────────────┤
│ 数据层  data/                       │  纯数据 + 纯查询
│         不含任何副作用方法            │
└─────────────────────────────────────┘
```

**关键约束：只有动作层能改数据。** 表现层点了一张真气，不能直接改 `qi.qi_zone` —— 它发一个信号，流程层构造一个 `ActionCirculateQi` 并执行。

这条约束的收益是拦截器有唯一的介入点。若表现层可以直接改数据，「敌方运转时反震」就必须在每个改数据的地方都写一遍。

## 3. 数据层：已完成

`data/` 下的类只有数据字段与**纯查询**方法。没有 `purify()`、`draw()` 这类会改状态的方法 —— 那些是动作的职责。

| 类 | 职责 |
|---|---|
| `QiData` | 一张真气：基础层（属性、内力）+ 重塑层 + 状态层 |
| `QiStateEntry` | 一条战斗状态（气力、毒、封脉…），只追加不修改 |
| `QiReshape` | 一条持久重塑，跨探索保留 |
| `BattleQiState` | 双方四牌区的容器，只负责搬数组，不做规则判断 |
| `QiEnums` | 五行、牌区、阵营枚举 |
| `NeigongData` | 内功配置与本局实例 |
| `QiInterceptorData` | 拦截器的固定配置 |

`BattleQiState.move_qi()` 的注释写明了这个边界：「不做任何规则检查 —— 封脉、行气上限、毒发都在动作里判断，这里只负责搬数组」。

## 4. 动作层：一次状态变更

一个动作 = 一次可被拦截的状态变更。

```text
BaseAction
  ├─ ActionCirculateQi     运转：行气 → 驭气
  ├─ ActionDrawQi          抽气：凝气 → 行气
  ├─ ActionDiscardQi       弃气：任意 → 散气
  ├─ ActionApplyQiState    施加状态：气力、毒、封脉
  ├─ ActionDamage          伤害：经过防御结算
  └─ ActionResolveGongfa   结算功法：读驭气、产生效果
```

### 4.1 执行流程

`BaseAction.execute()` 是模板方法，子类只重写 `_execute_core()`：

```text
execute()
  ├─ BEFORE 拦截链    可改参数、可拒绝
  ├─ _execute_core()  子类实现
  └─ AFTER 拦截链     只读结果、可追加效果
```

参数读写不直接碰 `values`，走 `resolver.get_shadowed_value()` —— 因此拦截器的修改对动作透明。

### 4.2 动作从哪拿到数据

**这是必须定下来的一件事。** 三种方案：

| 方案 | 做法 | 问题 |
|---|---|---|
| A 全局单例 | `Global.battle_qi_state` | 测试要初始化 autoload；同时跑两场战斗不可能 |
| B 上下文对象 | `action.context.battle_state` | 每次创建动作都要传 context |
| C 参数传入 | `action.set_action_value("battle_state", …)` | 拦截器可以改 battle_state，语义危险 |

**采用 B（上下文对象）。** `QiActionContext` 已经存在，收拢「动作要用到的外部能力」：查找真气、入队后续动作、发出事件。

流程层持有一个 `context`，创建动作时传进去。表现层不接触 context。

创建动作看起来是这样：

```gdscript
# 流程层（BattleFlow）内部
func player_circulate(qi_uids: Array[String], gongfa_uid: String) -> bool:
    var action := ActionCirculateQi.new()
    action.action_name = "运转"
    action.context = _context          # 流程层持有
    action.parent_combatant = _player
    action.source = ActionSource.from_gongfa(gongfa_uid, qi_uids, "玩家运转")
    action.set_action_value("qi_uids", qi_uids)
    action.set_action_value("target_zone", QiEnums.ZONES.PENDING)
    return action.execute()
```

**这段样板代码不应该出现在调用方。** 流程层对外暴露的是 `player_circulate(qi_uids, gongfa_uid)`，UI 只调这一句。

### 4.3 动作来源追踪

`ActionSource` 记录「谁产生的、为什么产生」，支持 `derive()` 形成链条：

```text
功法「万锋归宗」消耗真气 A、B
  → ActionResolveGongfa   source: gongfa=万锋归宗, qi=[A,B]
    → 触发内功「锋芒毕露」的拦截器
      → ActionDamage      source: 上者的 derive("锋芒出锋")
```

用途：战斗日志、「本回合第 N 次运转」这类计次、调试。

## 5. 流程层：待写

```text
battle/
  BattleFlow.gd        一场战斗：回合、行动组、先手判定
  Combatant.gd         战斗者：生命、防御层数、功法配置
  ActionQueue.gd       动作队列：处理动作产生动作
run/
  RunFlow.gd           一次探索：区域推进、撤离决策
  RunState.gd          探索状态：牌库、功法、内功、生命
```

### 5.1 战斗者

`Combatant` 不分玩家与敌人两个类 —— [敌方与信息](../game-design/05-敌方与信息.md) 已确定双方遵守同一套规则。用 `side: int` 区分。

```gdscript
class_name Combatant
var combatant_name: String
var side: int              # QiEnums.SIDES
var health: int
var health_max: int
var gongfa_list: Array     # 已配置的功法
var neigong_list: Array    # 已装备的内功
var defenses: Dictionary   # 护体罡气、岩障、化劲、格挡、灼热
```

拦截器的阵营判定靠 `registration.owner == action.parent_combatant` —— 比较的是 `Combatant` 实例，不读 `side`。

### 5.2 动作队列

动作会产生动作（运转 → 触发反震 → 伤害 → 触发死亡检查）。需要队列而非递归调用，否则调用栈会随连锁深度增长，且执行顺序不可控。

```gdscript
class_name ActionQueue
func enqueue(action: BaseAction) -> void
func enqueue_front(action: BaseAction) -> void   # 插到队首，用于必须立即结算的
func process_all() -> void                        # 跑到队列空
```

预览模式下 `enqueue()` 直接丢弃 —— 拦截器在预览时不应真的产生后续动作。这个开关由 `QiActionContext` 持有。

### 5.3 拦截器注册表挂哪

现在 `QiInterceptorResolver` 引用 `ActionHandler.qi_interceptors`，而 `ActionHandler` 已删。

改为挂在 `QiActionContext` 上：

```gdscript
# QiActionContext
var battle_state: BattleQiState
var interceptors: QiInterceptorRegistry
var action_queue: ActionQueue
var is_preview: bool
```

`resolver` 通过 `parent_action.context.interceptors` 拿到注册表。好处是不依赖 autoload，测试可以直接构造。

## 6. 表现层：待写

```text
scenes/
  Main.tscn            入口，切换探索与战斗
  Battle.tscn          战斗界面
ui/
  QiCard.gd            一张真气的显示
  ZonePanel.gd         一个牌区的显示
  GongfaSlot.gd        一门功法的显示与拖放目标
```

**表现层只做两件事：** 订阅流程层的信号刷新显示；把玩家操作转成对流程层的一次方法调用。

不允许：直接改 `QiData`、直接创建动作、直接读 `BattleQiState` 的私有字段。

## 7. 全局单例

只保留必要的两个：

| 单例 | 职责 |
|---|---|
| `Config` | 只读配置查询：功法数据、内功数据、拦截器配置、敌人配置 |
| `SaveGame` | 存档读写、局外进度 |

**不设 `Global.battle_state`。** 战斗状态由 `BattleFlow` 持有，通过 `context` 下传。这样测试可以构造一场独立战斗，不需要初始化 autoload。

配置数据用代码构造还是资源文件，见 [数据格式](./数据格式.md)（待写）。

## 8. 实现顺序

每一步都要能跑起来看到结果，不写一堆类再一起调。

```text
1. QiActionContext 补齐 interceptors / action_queue / is_preview
2. Combatant 最小版：name, side, health
3. ActionCirculateQi + 一个测试脚本，验证运转能改牌区
4. 接上一个拦截器（运转时气力 +2），验证 BEFORE 阶段生效
5. ActionQueue + ActionDamage，验证动作产生动作
6. BattleFlow 最小版：一个回合，抽 5 张，运转，结算一门功法
7. UI 最小版：显示行气的 5 张真气，点击能运转
```

第 3 步跑通就说明数据层与动作层的边界是对的。第 7 步跑通说明整条链路通了，之后是内容填充。

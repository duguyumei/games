# 组合出招：第一阶段可玩纵切

这是一个全新的 Godot 4.7 工程，依据 `godot/docs/design-current/README.md` 当前 v0.30
实现。它不引用原 `godot/` 项目的场景、脚本或测试。

开发流程、各节点质量门禁与当前架构债务见 `docs/development-workflow.md`。
模块边界与目标架构的详细审计见 `docs/architecture-audit.md`。

## 功法数量口径

功法设计唯一来源是 `godot/docs/design-current/README.md` 这份 v0.30 模块化权威源；
当前三个功法池模块分别记录风林蛊毒 29 门、风运转 38 门、火反击 40 门活跃候选。
当前 Godot 只保留 9 门可执行纵切样本，它们是运行测试夹具，不代表权威内容总量。
当前接入状态与剩余迁移范围见
`docs/technique-content-status.md`。

## 运行

在仓库根目录执行：

```bash
/Applications/Godot.app/Contents/MacOS/Godot \
  --log-file /tmp/taiwu-combo-play.log \
  --path combo_duel_vslice
```

图形启动不传模式时固定为 `production`，只装配正式构筑、地图、内容与敌人入口。
需要纵切脚本战斗、固定调试牌序或调试修习入口时，显式追加
`-- --launch-mode=development`。`test` 仅供自动化入口使用。

### 远程敌方 AI 配置

第一次以图形模式启动后，工程会生成：

```text
~/Library/Application Support/Godot/app_userdata/组合出招：第一阶段纵切/ai/ai_settings.cfg
```

关闭游戏后直接编辑该文件：在 `[provider]` 中填写 `api_key`，并把
`[remote_ai]` 下的 `enabled` 改为 `true`。默认使用 DeepSeek
`deepseek-v4-flash`、thinking 和 `medium` 推理强度；如需更高质量，可将模型改为
`deepseek-v4-pro`，并把 `reasoning_effort` 改为 `high`。完整字段示例见
`config/ai_settings.example.cfg`。

API Key 会以明文保存在这份本机配置中，因此不要提交或分享实际配置文件。它不会写入战斗
存档、结构化日志、公开快照或 `user://ai/conversations/` 下的脱敏会话。每次战斗尝试的会话
默认自动保存，只供审计、费用检查和回放；战斗中退出后从战斗开头建立新尝试，不续接旧
AI 对话。当前没有 AI 设置页面，也没有在确定性测试中访问真实网络。

界面流程：

1. 启动后先进入主菜单：新游戏、继续游戏、图鉴、记录、设置和退出游戏。继续游戏、图鉴、记录和设置目前只显示已确认范围，未确认的存档、条目和设置规则不会伪造实现。
2. 点击新游戏进入初始构筑页；当前唯一可选构筑是“四象周天”标准 52 张真气牌组（风、林、火、山各 13 张）。确认后建立 `RunSession`，用固定种子生成第 1 层路线并进入地图待选状态；起点剧情暂不接入。
3. 地图按固定种子生成 7 列、Boss 前 15 行、6 条起始路径的三层路线；商店节点不生成，原商店比例并入事件。
4. 金色边框表示当前可以选择的相连节点。进入节点后右下角修习按钮锁定；节点完成后先进入奖励结算，领取后返回地图并重新开放修习。
5. 修习页面采用卡片式固定代表选项，按钮下方显示当前历练。当前可购买高牌心得、教皇和光环；冥想费用、补货和正式商品数量未确认，因此不擅自实现。
6. 进入普通、精英或 Boss 节点时载入现有战斗纵切；胜利后生成可见奖励包，普通、精英和 Boss 分别提供 3、4、5 点历练。领取后返回地图或进入 Boss 宝箱，不自动打开修习。事件、休息和宝箱目前使用空奖励包与流程占位页，不补写未确认奖励。
7. 战斗会按指定种子洗牌，敌方从真实手牌枚举 1～5 张本地合法候选。启用远程 AI 后，每次主击或连击窗口都会异步请求选择候选；界面显示“思考中／思考完毕／本地接管”，思考完成前不能确认出牌或结束回合，但仍可修改选牌并使用只影响我方的消耗品。
8. 点击 1～5 张手牌，可预览精确牌型、参与真气、牌型基准值、功法值与循环功法；若双方都有有效行动意图则同步出招，只有一方能够行动时改为单方出招；随后按对应模式建立防御、标记与延迟记录、落地伤害并处理牌区。
9. 同属性行动会在每回合第一次满足时获得一次额外行动，但不会自动补牌；双方都有连击时继续同步，只有敌方有连击时由 AI 自动完成单方额外行动。
10. 纵切调试装配默认装备权威文档中的“初始内功候选”：额外打出但未参与最高牌型的真气值转化为防御；选牌预览会提前显示本次内功防御。
   内功栏右上角的“功法位”左右按钮可以调整动态功法与内功的实时结算顺序。
11. 顶部共享三格消耗品栏支持“高牌心得、教皇、光环”三个权威候选。
   点击槽位后按提示选择当前手牌并点击“使用”：心得提高指定精确牌型倍率并获得未拥有功法；
   教皇为至多两张真气施加奖励牌；光环按固定种子随机施加箔面、镭射或多彩。使用后释放
   槽位，强化／品相直接显示在卡面，目标会保留为出牌选择以便立即比较功法值。
12. 敌方生命归零时胜利；玩家生命归零或牌库与手牌均耗尽时失败。同一击双方倒下会停在“规则待确认”，不擅自判胜负。
13. 结束玩家回合可推进延迟记录；回合开始才正常补至手牌上限。当前无功法使用跨回合
   延迟追击（原 `百击归烬` 随同花池废弃），该机制的替代设计见火池文档「待确认」。

固定动作模式仍保留一条三回合确定性状态测试链：建立蛊印、附加烈毒，再由对手打出毒牌，
验证毒伤、蛊印消耗、续毒与洗回牌库。可玩界面默认使用调试 AI，不按这条测试脚本出牌。

## 数据与核心边界

- `core/content_catalog.gd`：一次性加载十二份版本化内容数据，建立真气、初始构筑、角色状态、强化、品相、印记、重塑·其他、异状、功法、内功、消耗品、节点、奖励与场景索引，并始终返回深复制查询结果。
- `core/content_validator.gd`：在战斗或本局建立前统一校验必填字段、类型、ID、52 张基础真气、重塑／异状容量与生命周期、功法池、序列、操作码、数值规格和跨文件引用。
- `core/game_composition_root.gd`：运行时组合根；每个本局使用同一内容目录、结构化日志、初始构筑仓库、构筑装配器与战斗会话工厂，避免 UI 和 `RunSession` 重复装配基础设施。
- `data/base_deck.json`：四属性、十三牌阶和真气值的唯一纵切数据入口。
- `data/starter_builds.json`：初始构筑定义；当前唯一构筑显式列出 52 个 `card_ids`，不再只用 `deck_kind` 作为占位标识。
- `data/battle_statuses.json`：角色战斗状态定义；当前登记蛊印与连势的层数、持续范围和战斗结束清理策略。
- `data/card_states.json`：本局重塑（强化、品相、印记、其他）与战斗异状（标记、毒、状态、其他）的容量、持续范围和弃牌清理规则。
- `core/technique_definition.gd`、`core/technique_instance.gd`：统一的功法内容实体与本局运行时实例；所有功法使用同一种类型。
- `data/techniques.json`：功法资源清单与共用池映射，不再保存功法正文。
- `data/techniques/*.tres`：每门功法一个独立资源文件；当前保存 9 门纵切运行样本，内容目录从这里加载、校验和建立索引。
- `data/inner_skills.json`：纵切内功定义与通用效果操作，当前只录入一门权威候选。
- `data/consumables.json`：三类代表性消耗品、目标数量和通用效果操作；不包含完整 52 种候选。
- `data/map_rules.json`：地图宽度、行数、路径数、固定节点行、节点权重与相邻约束。
- `data/node_content.json`：地图节点类型到战斗或未确认占位内容的调度配置；代表性战斗场景路径与 AI 开关不写死在地图 UI。
- `data/node_rewards.json`：节点奖励类型注册与基础战斗奖励；当前只实际定义权威确认的普通 3、精英 4、Boss 5 点历练，其他节点保持空数组。
- `data/vertical_slice_sequences.json`：仅供本纵切验证的调试装配，不是正式开局序列设计。
- `data/scripted_battle.json`：确定性敌方牌库、功法序列、固定测试动作与调试 AI 权重；都不是正式敌人构筑或正式 AI 规则。
- `core/hand_evaluator.gd`：九种普通牌型与参与数值计算真气的选择。
- `core/card_instance_id_factory.gd`：为复制、生成和夺取后的同定义真气生成确定性唯一实例 ID。
- `core/qi_card_instance_data.gd`：版本化真气实例 DTO；分开保存基础定义身份、本局重塑与可选的战斗异状，并校验全部内容引用。
- `core/run_deck.gd`：本局牌组的唯一权威状态；保存完整版本化真气实例，提供确定性复制、永久移出、战斗实例化和战后同步边界，拒绝临时真气与夺取牌混入本局。
- `core/card_state_lifecycle.gd`：根据内容定义执行开战生成异状、异状施加、进入弃牌堆和战斗结束生命周期；净化的屏蔽与恢复也由这里统一编排。
- `core/status_system.gd`：敌我共用的战斗状态入口；统一角色层数、真气异状、烈毒与蛊印续毒、延迟记录、时点结算、战斗结束清理和结构化状态历史。
- `core/status_change.gd`：状态变化 DTO；稳定记录目标、状态、前后值、来源与扩展元数据，供日志、快照和后续回放使用。
- `core/card_zone_service.gd`：统一执行抽牌、待出、回滚、正常打出、明确弃牌、回收、蛊印回库、燃尽、临时夺取／归还、战斗生成与永久移出；每次移动携带稳定原因，并在实际进入弃牌堆时调用异状生命周期。
- `core/actor_turn_state.gd`：每个战斗参与者独立保存行动次数、当前／后续禁用原因、连击占用、锁定意图和放弃行动原因，不区分玩家或敌人。
- `core/battle_flow_coordinator.gd`：通用行动窗口调度；只有至少两方都锁定有效意图时才选择同步结算，单方有意图时正常单独行动，并支持当前／后续回合禁用和零合法手牌放弃行动。
- `core/action_preview_service.gd`：无 UI 依赖的行动预览；统一完成选牌校验、牌型、功法值、功法条件、内功预计效果与连击预判。
- `core/damage_resolver.gd`：无 UI 依赖的伤害结算；统一处理普通伤害、真伤、连势增伤、同步伤害 shadow 与攻击段存活判断。
- `core/effect_executor.gd`：保持统一执行与预览接口的轻量兼容门面；效果链可以在指定下标暂停，并通过 continuation 从原位置恢复，不会重放已经完成的效果。
- `core/effects/technique_effect_context.gd`：类型化功法执行上下文；集中保存行动方、目标、牌型、功法值、来源、捕获结果与冻结选择数据，正式战斗路径不再向处理器传递完整引擎。
- `core/effects/battle_effect_ports.gd`：功法处理器使用的窄修改端口；统一代理伤害、防御、牌区、角色状态、真气异状、额外行动与延迟记录。
- `core/effects/effect_target_query.gd`：通用真气目标查询；统一阵营、牌区、牌库顶、固定种子随机顺序，以及属性、牌阶、普通／石头、重塑和异状筛选。
- `core/effects/battle_choice_request.gd`：可公开给 UI 或 AI 的选择契约；冻结候选、数量范围、选择方与明确的目标不足策略，并校验重复、越界和过期目标。
- `core/effects/technique_effect_continuation.gd`、`technique_effect_result.gd`：结构化保存效果下标、捕获结果与成功／失败／等待选择状态，支持非法选择后继续等待及多阶段连续选择。
- `core/effects/effect_handler_registry.gd`：把 15 个战斗操作码注册到七类能力处理器；拒绝未知或重复操作码，并允许新增处理器扩展。
- `core/effects/` 分组处理器：分别负责伤害、防御、牌区、真气异状、层数、流程／延迟和选择；共用递归数值规格、条件解析器与目标查询。
- `core/technique_repository.gd`、`core/inner_skill_repository.gd`、`core/consumable_repository.gd`：接收目录中已验证的深复制定义并提供领域查询；仍保留独立文件加载入口供兼容测试使用。
- `core/map_generator.gd`：按独立种子生成不交叉、可分叉汇合且能够抵达 Boss 的路线图。
- `ui/front_main.gd`：主菜单与初始构筑入口；只负责页面输入和场景切换，不直接生成地图。
- `core/starter_build_repository.gd`：消费已校验的初始构筑定义；当前只开放 `standard_52`。
- `core/starter_build_assembler.gd`：将构筑定义中的 `card_ids` 解析为真实 `RunDeck`；构筑选择不再只是快照元数据。
- `core/map_navigation_service.gd`：只管理本局地图种子、层数、流程阶段、当前节点、可达节点和换层。
- `core/growth_inventory.gd`：只管理历练、共享消耗品、心得、已获功法、完整 `RunDeck` 和修习购买记录。
- `core/run_progress_snapshot.gd`：战斗与本局之间的深复制成长传输对象；双方不再互相传递 Session 或领域对象。
- `core/node_dispatcher.gd`：把地图节点与本局上下文解析为确定性的内容调度结果，不直接创建 UI 场景或修改本局状态。
- `core/reward_bundle.gd`：版本化、可深复制的待领取奖励包，记录来源节点、种子、层数和奖励条目。
- `core/node_reward_service.gd`：按节点与固定上下文生成奖励包并通过 `GrowthInventory` 发放已实现奖励；拒绝未知奖励类型，不负责自我精进或未确认的先后顺序。
- `core/run_state.gd`：组合地图导航与成长库存的兼容门面；保留旧领域测试接口，新 UI 不直接访问。
- `core/run_session.gd`：本局应用层门面；统一接受建局、节点进入／完成、奖励领取、Boss 宝箱和修习命令，并负责节点调度、一次性奖励保护、价格校验、日志与事件。
- `core/run_snapshot.gd`：向地图与修习表现层提供深复制的只读本局快照，覆盖路线、可达节点、历练、成长背包、修习选项和日志。
- `core/run_event.gd`：可一次性消费的本局流程事件，用于后续地图动画、回放和诊断适配器。
- `core/trigger_queue.gd`：同一时点按顺序逐项结算；遇到选择时冻结当前条目和后续队列，恢复完成后再写入统一战斗日志并继续后续条目。
- `core/game_log.gd`：统一结构化日志服务；`battle`、`run` 与 `system` 三个通道共享稳定序号和字段，并保持各自语义隔离。
- `core/battle_setup_service.gd`：从本局成长快照和 `RunDeck` 装配战斗牌组、消耗品、心得与已获功法，并在战后只同步允许跨战斗的牌组实例状态。
- `core/battle_session_factory.gd`：战斗会话装配边界；由组合根创建并注入统一日志与内容目录。
- `core/battle_session.gd`：战斗应用层门面；统一接受开始回合、出牌、功法目标选择、结束回合、使用消耗品和调整功法位命令，并编排远程 AI 行动窗口门禁与敌方单方行动。
- `core/battle_snapshot.gd`：向表现层提供深复制的只读战斗快照；覆盖卡牌、内功、消耗品、等待选择请求以及战斗／系统日志，避免 UI 读取或修改领域对象。
- `core/battle_event.gd`：结构化战斗事件；可按序消费并用于后续动画、回放或文本调试器。
- `core/action_resolver.gd`：统一编排牌型组三阶段触发、左右顺序、选择暂停、牌上烈毒与蛊印回库、待出区提交和结算日志；成功后的序列推进注册在统一牌型组结束时点。
- `core/combat_engine.gd`：敌我独立序列、行动窗口、连击、可恢复行动事务与战斗结果；选择期间保持待出区和同步伤害状态，完成后才提交真气并推进序列。
- `core/battle_action_proposal.gd`：玩家输入、脚本敌人、本地 Utility 和远程候选共同输出的行动提案契约；支持第 0 主组与后续协同组，提案只描述“准备怎么行动”，不自行修改牌区或结算伤害。
- `core/battle_timing_event.gd`：单次战斗生命周期事件，保存时点、回合号、行动方、公开元数据和处理器结果。
- `core/battle_timing_system.gd`：统一战斗开始、完整回合开始、行动方回合开始、正常补牌前后、行动窗口开始／结束、牌型组结束、行动方回合结束和战斗结束；同一时点按 `order + 注册序号` 稳定调度处理器，内建处理器使用弱目标引用避免形成 RefCounted 环。
- `core/battle_observation.gd`：敌方决策所需的受限战斗观察；允许读取自身手牌，但只公开对手手牌数量，且不提供任一牌库顺序。
- `core/player_action_controller.gd`：把 UI 选牌转换为统一行动提案，并复用共享预览核完成合法性判断。
- `core/enemy_action_controller.gd`：分别适配脚本行动和数据驱动 Utility 行动，两者输出相同的行动提案。
- `core/scripted_battle_scenario.gd`：加载脚本化敌方测试场景并整理确定性敌方牌库。
- `core/enemy_combat_ai.gd`：数据驱动的纵切策略评分器；枚举自身真实手牌组合，使用必杀／已知致命威胁下的生存硬优先级、即时收益、过量伤害、连击后续手牌和序列偏好评分，并用可注入种子处理并列方案。
- `core/ai/action_window_ai_coordinator.gd`：独立异步行动窗口状态机；负责思考、门禁、超时、合法回答、本地复核、Utility 降级和公开意图状态，不拥有牌区或伤害结算权限。
- `core/ai/battle_ai_adapter.gd`：把共享战斗核投影为紧凑的战斗上下文、公开观察、合法候选和历史事件；隔离 `BattleSession` 与远程协议 DTO 的组装细节。
- `core/ai/ai_settings_service.gd`：读取或生成 `user://ai/ai_settings.cfg`，向组合根提供含凭据的运行时配置，同时只向快照暴露不含凭据的公开设置。
- `core/ai/ai_conversation_store.gd`：把每次战斗尝试的请求、回答、公开历史和压缩摘要递归脱敏后自动保存到 `user://ai/conversations/`；文件只供审计与回放，不用于续接战斗。
- `core/ai/` 其余协议模块：负责历史递归脱敏、无敌方行动窗口积压、每五回合工作历史压缩、响应校验与纠错、Provider 抽象及可审计会话快照。远程回答只能选择绑定本地 `BattleActionProposal` 的合法候选。
- `core/ai/providers/`：提供通用 OpenAI Chat Completions REST 适配器；默认 DeepSeek `https://api.deepseek.com/chat/completions` 与 `deepseek-v4-flash`，可选 `deepseek-v4-pro` 或自填兼容端点／模型。Godot 直接发送 HTTPS，不依赖 Python／Node SDK；API Key 仅从本机配置或 `DEEPSEEK_API_KEY` 环境变量读取，不进入公开快照、战斗存档、脱敏会话或审计请求。玩家设置页尚未实现，真实网络联调也未纳入确定性测试。

## 测试

在仓库根目录用统一入口串行执行。快速测试包含脚本／场景／JSON 加载、内容契约、
牌型与数值、功法契约和确定性测试：

```bash
./scripts/run_tests.sh quick
```

远程 AI 契约与 UI 加载，并自动发现其余顶层 `test_*.gd`：

```bash
./scripts/run_tests.sh full
```

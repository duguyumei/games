# 组合出招：第一阶段可玩纵切

这是一个全新的 Godot 4.7 工程，依据 `godot/docs/combo-duel-current.md` 当前 v0.28
实现。它不引用原 `godot/` 项目的场景、脚本或测试。

当前模块边界、耦合风险与目标架构见 `docs/architecture-audit.md`。

## 运行

在仓库根目录执行：

```bash
/Applications/Godot.app/Contents/MacOS/Godot \
  --log-file /tmp/taiwu-combo-play.log \
  --path combo_duel_vslice
```

界面流程：

1. 主场景按固定种子生成 7 列、Boss 前 15 行、6 条起始路径的三层路线地图；商店节点不生成，原商店比例并入事件。
2. 金色边框表示当前可以选择的相连节点。进入节点后右下角修习按钮锁定；节点完成并返回地图后重新开放。
3. 修习页面采用卡片式固定代表选项，按钮下方显示当前历练。当前可购买高牌心得、教皇和光环；冥想费用、补货和正式商品数量未确认，因此不擅自实现。
4. 进入普通、精英或 Boss 节点时载入现有战斗纵切；胜利后获得对应历练并直接返回地图，不自动打开修习。事件、休息和宝箱目前使用流程占位页。
5. 战斗会按指定种子洗牌，敌方从真实手牌枚举 1～5 张选牌并锁定行动，界面只公开预计伤害、预计防御和连击提示。
6. 点击 1～5 张手牌，可预览精确牌型、参与真气、牌型基准值、功法值与循环功法；若双方都有有效行动意图则同步出招，只有一方能够行动时改为单方出招；随后按对应模式建立防御、标记与延迟记录、落地伤害并处理牌区。
7. 同属性行动会在每回合第一次满足时获得一次额外行动，但不会自动补牌；双方都有连击时继续同步，只有敌方有连击时由 AI 自动完成单方额外行动。
8. 纵切调试装配默认装备权威文档中的“初始内功候选”：额外打出但未参与最高牌型的真气值转化为防御；选牌预览会提前显示本次内功防御。
   内功栏右上角的“功法位”左右按钮可以调整动态功法与内功的实时结算顺序。
9. 顶部共享三格消耗品栏支持“高牌心得、教皇、光环”三个权威候选。
   点击槽位后按提示选择当前手牌并点击“使用”：心得提高指定精确牌型倍率并获得未拥有功法；
   教皇为至多两张真气施加奖励牌；光环按固定种子随机施加箔面、镭射或多彩。使用后释放
   槽位，强化／品相直接显示在卡面，目标会保留为出牌选择以便立即比较功法值。
10. 敌方生命归零时胜利；玩家生命归零或牌库与手牌均耗尽时失败。同一击双方倒下会停在“规则待确认”，不擅自判胜负。
11. 结束玩家回合可推进 `百击归烬` 等延迟记录；回合开始才正常补至手牌上限。

固定动作模式仍保留一条三回合确定性状态测试链：建立蛊印、附加烈毒，再由对手打出毒牌，
验证毒伤、蛊印消耗、续毒与洗回牌库。可玩界面默认使用调试 AI，不按这条测试脚本出牌。

## 数据与核心边界

- `core/content_catalog.gd`：一次性加载十份版本化内容数据，建立真气、角色状态、强化、品相、印记、重塑·其他、异状、功法、内功、消耗品、节点与场景索引，并始终返回深复制查询结果。
- `core/content_validator.gd`：在战斗或本局建立前统一校验必填字段、类型、ID、52 张基础真气、重塑／异状容量与生命周期、功法池、序列、操作码、数值规格和跨文件引用。
- `data/base_deck.json`：四属性、十三牌阶和真气值的唯一纵切数据入口。
- `data/battle_statuses.json`：角色战斗状态定义；当前登记蛊印与连势的层数、持续范围和战斗结束清理策略。
- `data/card_states.json`：本局重塑（强化、品相、印记、其他）与战斗异状（标记、毒、状态、其他）的容量、持续范围和弃牌清理规则。
- `data/techniques.json`：六个共用池映射与代表性功法效果描述。
- `data/inner_skills.json`：纵切内功定义与通用效果操作，当前只录入一门权威候选。
- `data/consumables.json`：三类代表性消耗品、目标数量和通用效果操作；不包含完整 52 种候选。
- `data/map_rules.json`：地图宽度、行数、路径数、固定节点行、节点权重与相邻约束。
- `data/node_content.json`：地图节点类型到战斗或未确认占位内容的调度配置；代表性战斗场景路径与 AI 开关不写死在地图 UI。
- `data/vertical_slice_sequences.json`：仅供本纵切验证的调试装配，不是正式开局序列设计。
- `data/scripted_battle.json`：确定性敌方牌库、功法序列、固定测试动作与调试 AI 权重；都不是正式敌人构筑或正式 AI 规则。
- `core/hand_evaluator.gd`：九种普通牌型与参与数值计算真气的选择。
- `core/card_instance_id_factory.gd`：为复制、生成和夺取后的同定义真气生成确定性唯一实例 ID。
- `core/qi_card_instance_data.gd`：版本化真气实例 DTO；分开保存基础定义身份、本局重塑与可选的战斗异状，并校验全部内容引用。
- `core/run_deck.gd`：本局牌组的唯一权威状态；保存完整版本化真气实例，提供确定性复制、永久移出、战斗实例化和战后同步边界，拒绝临时真气与夺取牌混入本局。
- `core/card_state_lifecycle.gd`：根据内容定义执行开战生成异状、异状施加、进入弃牌堆和战斗结束生命周期；净化的屏蔽与恢复也由这里统一编排。
- `core/status_system.gd`：敌我共用的战斗状态入口；统一角色层数、真气异状、烈毒与蛊印续毒、延迟记录、时点结算、战斗结束清理和结构化状态历史。
- `core/status_change.gd`：状态变化 DTO；稳定记录目标、状态、前后值、来源与扩展元数据，供日志、快照和后续回放使用。
- `core/card_zone_service.gd`：统一执行抽牌、待出、回滚、正常打出、明确弃牌、回收、蛊印回库、燃尽、临时夺取／归还、战斗生成与永久移出；每次移动携带稳定原因，并在实际进入弃牌堆时调用异状生命周期。
- `core/actor_turn_state.gd`：每个战斗参与者独立保存行动次数、当前／后续禁用原因、连击占用、锁定意图和放弃行动原因，不区分玩家或敌人。
- `core/battle_flow_coordinator.gd`：通用行动窗口调度；只有至少两方都锁定有效意图时才选择同步结算，单方有意图时正常单独行动，并支持当前／后续回合禁用和零合法手牌放弃行动。
- `core/action_preview_service.gd`：无 UI 依赖的行动预览；统一完成选牌校验、牌型、功法值、功法条件、内功预计效果与连击预判。
- `core/damage_resolver.gd`：无 UI 依赖的伤害结算；统一处理普通伤害、真伤、连势增伤、同步伤害 shadow 与攻击段存活判断。
- `core/effect_executor.gd`：保持统一执行与预览接口的轻量兼容门面，不再包含中央操作码大分支。
- `core/effects/effect_handler_registry.gd`：把 14 个战斗操作码注册到六类能力处理器；拒绝未知或重复操作码，并允许新增处理器扩展。
- `core/effects/` 分组处理器：分别负责伤害、防御、牌区、真气异状、层数、流程／延迟；共用递归数值规格与条件解析器。
- `core/technique_repository.gd`、`core/inner_skill_repository.gd`、`core/consumable_repository.gd`：接收目录中已验证的深复制定义并提供领域查询；仍保留独立文件加载入口供兼容测试使用。
- `core/map_generator.gd`：按独立种子生成不交叉、可分叉汇合且能够抵达 Boss 的路线图。
- `core/map_navigation_service.gd`：只管理本局地图种子、层数、流程阶段、当前节点、可达节点和换层。
- `core/growth_inventory.gd`：只管理历练、共享消耗品、心得、已获功法、完整 `RunDeck` 和修习购买记录。
- `core/run_progress_snapshot.gd`：战斗与本局之间的深复制成长传输对象；双方不再互相传递 Session 或领域对象。
- `core/node_dispatcher.gd`：把地图节点与本局上下文解析为确定性的内容调度结果，不直接创建 UI 场景或修改本局状态。
- `core/run_state.gd`：组合地图导航与成长库存的兼容门面；保留旧领域测试接口，新 UI 不直接访问。
- `core/run_session.gd`：本局应用层门面；统一接受建局、节点进入／完成、Boss 宝箱和修习命令，并负责节点调度、价格校验、日志与事件。
- `core/run_snapshot.gd`：向地图与修习表现层提供深复制的只读本局快照，覆盖路线、可达节点、历练、成长背包、修习选项和日志。
- `core/run_event.gd`：可一次性消费的本局流程事件，用于后续地图动画、回放和诊断适配器。
- `core/trigger_queue.gd`：同一时点按顺序逐项结算，并把结算结果写入统一战斗日志通道。
- `core/game_log.gd`：统一结构化日志服务；`battle`、`run` 与 `system` 三个通道共享稳定序号和字段，并保持各自语义隔离。
- `core/battle_setup_service.gd`：从本局成长快照和 `RunDeck` 装配战斗牌组、消耗品、心得与已获功法，并在战后只同步允许跨战斗的牌组实例状态。
- `core/battle_session.gd`：战斗应用层门面；统一接受开始回合、出牌、结束回合、使用消耗品和调整功法位命令。
- `core/battle_snapshot.gd`：向表现层提供深复制的只读战斗快照；覆盖卡牌、内功、消耗品展示数据以及战斗／系统日志，避免 UI 读取或修改领域对象。
- `core/battle_event.gd`：结构化战斗事件；可按序消费并用于后续动画、回放或文本调试器。
- `core/action_resolver.gd`：统一编排牌型组三阶段触发、左右顺序、牌上烈毒与蛊印回库、待出区提交和结算日志；成功后的序列推进注册在统一牌型组结束时点。
- `core/combat_engine.gd`：敌我独立序列、行动窗口、连击与战斗结果；行动资格、同步／单方模式、行动、伤害和状态分别委托 `BattleFlowCoordinator`、`ActionResolver`、`DamageResolver` 与 `StatusSystem`。
- `core/battle_action_proposal.gd`：玩家输入、脚本敌人和策略敌人共同输出的行动提案契约；提案只描述“准备怎么行动”，不自行修改牌区或结算伤害。
- `core/battle_timing_event.gd`：单次战斗生命周期事件，保存时点、回合号、行动方、公开元数据和处理器结果。
- `core/battle_timing_system.gd`：统一战斗开始、完整回合开始、行动方回合开始、正常补牌前后、行动窗口开始／结束、牌型组结束、行动方回合结束和战斗结束；同一时点按 `order + 注册序号` 稳定调度处理器，内建处理器使用弱目标引用避免形成 RefCounted 环。
- `core/battle_observation.gd`：敌方决策所需的受限战斗观察；允许读取自身手牌，但只公开对手手牌数量，且不提供任一牌库顺序。
- `core/player_action_controller.gd`：把 UI 选牌转换为统一行动提案，并复用共享预览核完成合法性判断。
- `core/enemy_action_controller.gd`：分别适配脚本行动和数据驱动 Utility 行动，两者输出相同的行动提案。
- `core/scripted_battle_scenario.gd`：加载脚本化敌方测试场景并整理确定性敌方牌库。
- `core/enemy_combat_ai.gd`：数据驱动的纵切策略评分器；枚举自身真实手牌组合，使用必杀／已知致命威胁下的生存硬优先级、即时收益、过量伤害、连击后续手牌和序列偏好评分，并用可注入种子处理并列方案。
- `core/ai/`：独立远程 AI 协议模块；负责版本化战斗上下文、公开观察与历史脱敏、无敌方行动窗口的事件积压、每五回合工作历史压缩、主组／协同组候选、响应校验与纠错重试、Provider 抽象及可恢复会话快照。远程回答只能选择绑定本地 `BattleActionProposal` 的合法候选；当前第一步仅接入 Mock Provider 测试，不调用真实网络，也尚未接管战斗行动窗口。

## 测试

```bash
/Applications/Godot.app/Contents/MacOS/Godot \
  --headless \
  --log-file /tmp/taiwu-combo-tests.log \
  --path combo_duel_vslice \
  --script res://tests/test_runner.gd
```

基础值与功法值公式、序列成功/失败推进、代表性功法、延迟 P 快照、可见队列顺序、

玩家／敌方行动生成边界、受限 AI 观察、必杀和非贪心连击规划、脚本敌方锁定、
调试 AI 的确定性与公开计划脱敏、敌方单方/双方同步连击、
远程 AI 观察与历史的递归脱敏、单方连击历史积压和下次发送、主组／协同组复合候选、
非法回答纠错重试、本地行动提案绑定、每五回合压缩、Provider epoch 与脱敏会话恢复，
内功未装备/装备效果、额外真气转化、敌我独立装备、功法与内功左右顺序、
同步防御/伤害、敌我独立序列、胜负、未决同归于尽，以及
烈蛊飞针附毒、烈毒触发、蛊印消耗、续毒和洗回牌库的完整确定性状态链。
伤害模块另有直接确定性测试，覆盖防御优先吸收、真伤绕过防御、连势增伤、
目标死亡停止后续攻击段、同步双方致命，以及 `CombatEngine` 兼容门面与独立服务等价性。
此外覆盖统一内容目录的版本、ID 唯一性、操作码、递归数值规格、功法池资格、真气与场景引用、深复制查询和战斗／本局共享装配，
以及效果处理器注册完整性、六类能力路由、未知／重复操作码拒绝和动态处理器扩展，
以及三格共享容量、满格不生成、使用后释放、精确牌型心得倍率、未拥有功法获取、
奖励牌强化替换、箔面／镭射／多彩品相、重塑／异状容量与净化恢复、地图确定性、固定行与节点约束、不交叉路线、
Boss 可达性、节点进行中修习锁定、战后历练和跨战斗构筑持久化。
`RunDeck` 测试另覆盖 52 张初始化、完整重塑同步、异状隔离、唯一实例 ID、确定性复制、永久移出、临时真气拒绝、版本化快照恢复，以及 `RunDeck → BattleSetupService → 战斗结算快照` 的端到端边界。
其中包含在战斗中实际使用“光环”施加品相、消耗槽位，并由下一场战斗从 `RunDeck` 恢复同一重塑实例的确定性测试。
牌区服务测试覆盖待出回滚、弃牌清理、回收不恢复异状、蛊印绕过弃牌堆、燃尽不误删本局牌、永久损毁登记、临时生成，以及跨阵营夺取与归还。
行动调度测试覆盖任意参与者状态、单方／同步意图判定、当前与后续回合禁用、禁用期间获得行动、零手牌放弃行动、连击占用，并包含敌方被禁用、玩家被禁用和敌方补牌后仍为零手牌的实际战斗集成场景。
本局会话测试另覆盖命令拒绝、节点调度、快照深复制、核心定价、事件消费、地图导航／成长库存职责边界、
成长快照导入导出，以及地图、修习、战斗共用日志实例。

战斗界面的“结算记录”面板可以切换战斗日志与系统日志。战斗日志记录牌型、队列、
伤害和牌区结算；本局日志记录建局、节点、Boss 宝箱、修习与成长同步；系统日志记录
会话建立、命令拒绝与脚本场景故障。三个通道使用同一结构化记录服务和稳定序号，但不会
混在同一玩家播报中。Godot 进程自身的错误仍通过每次运行指定的
`--log-file /tmp/...` 写入磁盘诊断日志。

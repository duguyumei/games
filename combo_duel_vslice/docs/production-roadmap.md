# 组合出招生产开发排期

- 状态：当前执行排期
- 日期：2026-08-07
- 适用工程：`combo_duel_vslice/`

本文件只安排开发顺序、周期与完成门禁，不定义游戏规则。规则唯一权威源仍是
`godot/docs/design-current/README.md`；任何未确认规则必须先写入对应权威模块，才能进入实现。

项目目标是完成一款可以长期维护、扩展、游玩和发布的卡牌游戏。阶段性可玩构建只是内部
集成与试玩里程碑，不是“纵切 Demo”产品终点。

## 排期与调度假设

- 表中的“周期”是日历时间；任务工作量按负责人工作日估算。
- 默认由一个总控任务负责审查、串行测试和提交，最多同时运行两个文件所有权不重叠的执行任务。
- 所有任务直接使用 `/Users/cc/Documents/taiwu`，不创建分支或 worktree。
- 每个执行任务必须限定文件所有权；不得覆盖其他任务修改，不自行提交。
- 核心流程改造按顺序集成；内容、UI、美术和文档只有在文件范围不重叠时才并行。
- 完整测试串行运行。阶段按验收门禁推进，不因预计日期到达而自动结束。

## 三类工作

架构审计中的“值得改进”不自动等于“内容生产前必须完成”。所有工作按以下三类调度。

### A · 一次性建好并验收

这类工作负责建立稳定协议或完整产品闭环。完成验收后以修缺陷和兼容演进为主，不反复重写。

| 模块 | 所属阶段 | 一次性完成标志 | 阻塞范围 |
|---|---|---|---|
| 当前类型化重构与干净基线 | S0（已完成） | 命令结果、事件、运行快照和 AI 边界已在 `0555d0f` 验收 | 不再阻塞 S1 |
| 功法效果与状态处理器协议 | S1（1.3 已完成） | 风林蛊毒、火系探针都能通过注册处理器接入 | 只阻塞依赖新状态语义的内容 |
| 三层本局与节点存档闭环 | S2 | 任意节点边界保存、恢复和继续流程一致 | 阻塞完整三层试玩 |
| 内功时点、修正器与否决协议 | S4 | 验证内容覆盖战斗内外和规则拦截 | 阻塞内功大批量录入 |
| 发布与产品验收管线 | S8 | 设置、导出、迁移、许可和发布回归通过 | 阻塞 v1.0 发布 |

以下基础已经完成，不重新设为 S0 前置：组合根与内容失败快停、core/UI 快照类型化、效果规格
校验器拆分、第一轮 UI 组件边界、存档 v1、AI 合法候选与脱敏边界。

### B · 从现在持续到发布

这类工作没有“一次做完以后永远不碰”的状态，按内容批次和试玩反馈持续推进，但不能阻塞
无关模块。

| 长期轨道 | 持续工作 | 节奏 |
|---|---|---|
| 内容生产 | 功法、内功、消耗品、敌人、事件、Boss 与奖励录入 | 每批内容独立校验和测试 |
| UI 与美术 | 场景化组件、Theme、语义资源目录、动画、特效、音频与可读性 | 跟随实际页面和内容交付 |
| 测试质量 | 新规则回归、领域测试拆分、架构守卫、存档兼容样本 | 每次行为变更同步增加 |
| 架构健康 | 消除本次改动撞到的重复流程、过宽端口和隐式依赖 | 小步提交，不进行泛化重写 |
| 试玩与平衡 | 牌型频率、构筑分歧、经济、难度、单局时长和体验问题 | S3 起持续到发布后 |
| 文档与可维护性 | Java 对照说明、模块职责、不变量、扩展步骤和变更记录 | 模块稳定或扩展时更新 |
| 性能与稳定性 | 触发队列、快照、存档、AI 上下文、加载和长局稳定性 | 先设预算，S6 后集中压测 |

`CombatEngine` 瘦身、`StatusSystem` 继续拆分、UI 全面场景化和测试 runner 拆分属于这条长期
轨道。它们要持续做，但不再作为 S1 开始前必须清零的“大架构阶段”。

### C · 需求出现时再建

这类模块提前建设容易产生没有使用者的抽象，只在触发条件出现时完成。

| 触发条件 | 届时完成的模块 | 不提前做的原因 |
|---|---|---|
| 准备加入第二种战斗流程或敌方控制方式 | 用“战斗流程类型 + 敌方控制类型”替代模式布尔，并在建局时一次注入 | 当前单一正式流程不需要完整模式框架 |
| 准备发布存档 v2 | 明确 `RunSession` 存档 payload、迁移与回滚契约 | 当前 v1 已能保存，避免与正在进行的 DTO 改造叠加 |
| 第二种奖励类型真正接入 | 奖励处理器注册表 | 只有一种奖励时注册表没有扩展收益 |
| 两个以上模块反复需要同一战斗状态读写 | 小型 `BattleStateGateway` 实验 | 当前窄端口足够，不把实验升级为硬前置 |
| 新内容持续要求修改同一中央流程 | 抽出对应能力模块或事务 | 由真实重复证明抽象边界，不为未来猜测 |

## 阶段调度规则

每个阶段开始时，由总控任务把表中事项拆成独立 Codex 任务，并先标记为“一次性”“长期批次”
或“条件触发”。任务必须记录：目标、允许修改文件、禁止修改文件、依赖、验收命令和交付说明。
任务完成后按以下顺序集成：

1. 总控审查实际 diff，拒绝超出文件所有权的修改。
2. 先运行受影响的窄测试，再串行运行完整测试。
3. 检查 Godot stdout 与日志中的 `Can't load script`、`File not found` 和其他错误。
4. 更新本排期的阶段状态、内容接入状态和架构债务记录。
5. 由总控统一提交，形成下一个干净基线后再派发重叠范围的任务。

长期轨道每次只领取一个有具体使用者的批次，不创建“把整个引擎重构完”“把所有 UI 一次性
组件化”这类没有可验收边界的任务。条件触发模块在触发条件尚未出现时只保留记录，不派发实现。

## 0. 一句话总览

**一款"二人麻将 + Balatro"的肉鸽卡牌构筑游戏**：底层是双人对弈麻将（吃碰杠听牌俱全），但"和牌"不是终局而是**可重复的计分动作**——和一次牌 = 按 `底分×番数×独立倍率` 结一次分；战斗胜负 = **分数竞速**（玩家冲 Boss 的 targetScore，Boss 冲自己的 LimitScore）；局外是杀戮尖塔式地图（章/层/小节、商店、事件），构筑深度来自 470+ 个小丑牌/灵俑类、159 个宝牌、祭品、宝灵、角色技能。

## 1. 游戏总循环（从代码与文案还原）

```
主菜单 → 选角色（1主动技能＋1被动技能，主动耗魂力）
       → 肉鸽地图（章 → 层组 → 小节组 → 节点：战斗/商店/事件/精英/Boss）
           战斗节点 = 一场二人麻将对弈（见 §2）
           商店 = 小丑牌商店 / 代币商店 / 精魄商店（卖灵俑）
           事件 = 自研节点图系统（GameEvent.Runtime，114 个节点类）
       → 和牌计分冲 targetScore → 赢：掉落奖励 → 输：扣局外生命 → 死亡：复活道具或结算
局外成长：天赋树（Talent.Runtime）· 成就（Achievement.Runtime 77 类）· DLC 内容表 · 多周目难度（DifficultyPayload）
```

关键判定（代码证据）：
- `PlayMaJiangData { Level, AIBase, RandomLingYongIndex×4, targetScore: Decimal, randomSeed, offeringSlotNumExceed }` —— 进战斗的完整输入就是这些。
- `PlayerPipeline.RoundEndState = { None, Draw, PlayerWin, AIWin }` —— 对弈四种终局。
- `ScoreBoard.SetupBossLimitScore(DifficultyPayload, aiTargetScore)` + `_aiLimitScoreEnabled/_aiLimitScore` —— Boss 有自己的分数上限，形成**双向竞速**。
- `PlayerHp { hpMax, Hp, TempPositive, TempNegative, TempAddHp }` —— 局外肉鸽血量，含临时正/负血（类尖塔格挡的临时层）。
- 教学文案原话（元数据字符串）："当你满足听牌条件时，就可以选择听牌；听牌指示区会显示你可以和的牌及剩余的数量"；"听牌后，你不能再吃碰，也不能再换牌了，摸到的牌会被自动打出，此时需要耐心等待可以和的牌出现"。

## 2. 麻将对弈规则（核心玩法层）

### 2.1 牌与牌山

- **牌结构** `PaiMian`（struct，[BurstCompile] 热路径值类型）：
  `{ HuaSe huaSe; int number; Feng feng; Jian jian }`
  - `HuaSe = { None, 万, 筒, 索(条), Any }` —— **三门数牌＋字牌**，`Any` 是给小丑/宝牌查询用的通配值。
  - `Feng = { None, 东南西北, Any }`；`Jian = { None, 中, 白, 发, Any }`（注意顺序：中=1、白=2、发=3）。
  - `PaiMianType`（查询用复合枚举）：None/-1、Any=0、一~九=1..9、数牌/小(1-3)/中(4-6)/大(7-9)/幺九=10..14、字=20、万=21、筒=22、索=23…——**这是内容查询的"牌面谓词"层**，小丑牌描述（"你持有大数牌时…"）直接用这组词。
- **牌山** `AllPaiMianContainer`（共享，双方同摸一座山）：
  - `Pop / PopLast / PopCount / PreFetch`（预看）/ `InsertBackEnd` / `AddToTop / AddToBottom / InsertBackRandom / AddRandom` —— **顶/底/随机三向插牌**，宝牌与小丑可以干预山（塞牌、藏牌）。
  - 牌的具体构成（几副、含不含字）在 `PaiMianPayloadList` ScriptableObject 资产里，本次未解出 typetree（见 §7 未解之谜）。
- **弃牌区** `DiscardContainer`（长度可配 `discardContainerLength`）、**弃换区** `DiscardSwap`（`SwapType = { None, PlayerDiscardSwap, AiDisCardSwap, PlayerAndAiDisCardSwap, PlayingSwap }`）——打出/换走的牌进公共可见区，吃碰杠素材从打出流里截。

### 2.2 回合引擎（InRoundTurn 状态机）

`InRoundTurn = { InitSwap(0) → PlayerSwap(1) → PlayerPlayAIChiPengGang(2) → AISwap(3) → AIPlayPlayerChiPengGang(4) → InAnGang(5) → InJiaGang(6) → InChiPengMingGangDiscard(7) → InJiFen(8) }`

一拍的完整流程（对照 PlayerPipeline/AIPipeline 方法族还原）：

1. **InitSwap 初始调度**：起手抽手牌（`OnFetchHand`），玩家可调度换 N 张（`initSwapPaiTotal`，`OnFetchSwap`）。
2. **PlayerSwap 玩家回合**：`OnBeforeFetchStart`（小丑可加手牌/花色感染手牌）→ 摸牌（`IGetMoPaiNum` 可改摸牌数）→ 换牌（`swapPaiTurnTotal` 张，`OnSwapStart`；换牌余量 `PlayerSwapPaiLeftCount` 单独记账）→ **打出**（`OnPlaying/OnSliding`，打出的牌开吃碰杠窗口）。
3. **PlayerPlayAIChiPengGang**：对方（AI）决定吃/碰/明杠（`OnRunChiPengMingGang`），窗口内还有加杠（`OnRunJiaGang`）、暗杠（`InAnGang`，不依赖打出）。
4. **AISwap / AIPlayPlayerChiPengGang**：镜像一轮（玩家这边获得吃碰杠窗口，`OnEnterPlayerAvailableChiPeng`）。
5. **InJiFen 计分**：见 §2.4。

**没有传统"顺位轮转"**——就是双人你来我往，吃碰杠不消耗行动权（麻将原生），这点与我们 v3 拍板一致。

### 2.3 听牌（Ting）

- 触发：满足听牌条件时可**主动选择听牌**（`OnTing`，教学文案确认是选择而非强制）。
- 效果：**锁死**——不能再吃碰、不能再换牌，摸到的牌**自动打出**，纯等和牌（等牌数与剩余张数显示在听牌指示区，悬停可看和牌番型）。
- 节奏补丁：**和牌加速按钮**（`TimeScaleButton`，"觉得听牌后时间过得太慢吗？试试加速吧"）——听牌后是纯随机等待，官方方案是快进而不是改规则。
- `TingStatistics`（struct）：`{ round, handPaiList: PaiStatistics[], chiPengGangList: ChiPengGangStatistics[] }` + 每次和牌的 `{ fromOtherSide, huPai, fanZhongList[], baseScore: Decimal, fan: Decimal, independent: Decimal }`。
- AI 侧：`GreedyConfig.needDelayTing / delayTing / delayMin / delayMax` —— **AI 故意延迟听牌**做节奏控制（防止 Boss 瞬间听牌碾压玩家）。
- `RoundHuFirst = { None, AI, Player }`：记录谁先和的牌（先和有加成语义，数值在资产）。

### 2.4 和牌与计分（本作最核心的改造）

**和牌 ≠ 终局，和牌 = 一次计分入账**。对弈持续多轮，靠和牌槽控制次数。

- **和牌分解** `HuResult`（struct）：
  `{ SpecialHuType: HuType[Flags], FanZhongs: ICollection<FanZhong>, DuiList, ShunList, KeList, ChiList, PengList, AnGangList, MingGangList, OtherList }`
  —— 和牌手被完整分解成 对子/顺子/刻子/吃/碰/暗杠/明杠 列表＋番种集合，**所有小丑的"你每有一个刻子…"类效果都从这份分解里数**。
- **特殊牌型** `HuType [Flags]`：`Normal / QiDui七对 / LianQiDui连七对 / ShiSanYao十三幺 / GuYiYuanZhouLv / QuanBuKao全不靠 / QiXingBuKao七星不靠 / ZuHeLong组合龙 / GuYiWuFuLinMen / GuYiErCiFang / GuYiTianXiaWuShuang`（位掩码，可叠加判定）。
- **计分公式**（`OnHuOutput` / `OnJiFenOutput` 字段直接给出）：

  ```
  Δ总分 = AccBaseScore(累计底分) × AccFan(累计番数) × AccIndependent(累计独立倍率)
  附加：AddCoin(金币) · TempIndependentPayloads(临时倍率) · NeedApplyBaoLingDisplays(宝灵附着)
       · BossCaskSkill(Boss 技能拦截) · DelayAnimations(结算动画队列)
  ```

  全程 `Decimal`（防浮点漂移——**构筑游戏的分数必须精确**）。
- **和牌槽 HuPaiSlots**：`GvHuSlotCount` 起始值＋`huPaiSlotsCountSoftLimit/HardLimit` 软硬上限＋`OnHuSlotCountUpdate/IGetHuPaiSlotsCount`（小丑可加减槽）——**一局对弈里你能"存"几次和牌**，把"麻将一局一和"改造成"一局多和、次数稀缺"。
- **运气事件**：`IOnHaoYun好运 / IOnEYun厄运 / IOnZhongYun中运` 钩子＋文案"灵俑 {0} 触发好运，独立倍率 +{1}%"＋统计项"一轮游戏累计触发好运次数"——**运气 = 随机触发的倍率事件**，小丑可挂钩。
- **金币**：和牌产出金币（局内/局外两套乘区 `inGameCoinsMulti/outGameCoinsMulti`），用于商店经济。

### 2.5 胜负与血量

- 局内：分数竞速（§1）。`InRoundStatistics.FinalStatistics { gameSeed, battleSeed, bossId, totalTurn, playerScore, aiScore }` 出终局比分。
- 局外：`PlayerHp`（含临时正/负血）在战败/事件里掉血，死亡走 `NearDeathCheck(IReviveItem)` 复活道具检查。
- 难度：`DifficultyPayload { ID, Icon, RewardDescription, PunishmentDescription, XiaoChouPaiPayloads }` —— 难度既是惩罚也是奖励池。

## 3. 构筑与内容层（这游戏 90% 的代码量在这）

### 3.1 小丑牌/灵俑（同族代码，两个名字）

- 玩家侧局内叫**小丑牌**（`MaJiang.PlayMaJiang.Player.PlayerXiaoChouPai`，dump 计 286 类）；敌方 Boss 持有的叫**灵俑**（`AIXiaoChouPai` 185 类；`AIBase.RandomXiaoChouPool×4` 抽取；文案"对手除了会有主动技能，也会有自己的灵俑"）；局外收集形态也叫灵俑（精魄商店出售、"孵化灵俑"、灵俑仓库 `GvLingyongRepositorySlotNum`）。**代码上是同一个 XiaoChouPai 家族**。
- **实现范式（对我们最有参考价值）**：每张小丑 = 一个 `XiaoChouPaiDisplay` 子类，**按需实现钩子方法**，全部走 `(OnXxxInput input, OnXxxOutput output)` 数据协议。例：八哥（BaGe）只实现三个钩子——`OnXiaoChouInitApply`（入场）、`OnHu`（和牌时）、`OnMaJiangRoundEnd`（回合末结算 Diff）。
- **钩子接口族** `MaJiang.PlayMaJiang.XiaoChouPaiCommon.Interfaces`（90 个）：

  | 类别 | 接口（节选） |
  |---|---|
  | 摸/换 | IOnBeforeFetchStart, IOnFetchHand, IOnFetchSwap, IOnFetchLast(岭上), IOnBeforeInitSwap, IOnBeforeSwapStart, IOnSwapStart, IOnBeforeSwapStartAddSwapPaiMians, **IGetMoPaiNum**(改摸牌数), IGetTotalPaiNum |
  | 打出 | IOnPlaying, IOnSliding, IOnDiscard, IOnPaiDiscardSetChanged, IOnPaiMianChanged |
  | 吃碰杠 | IOnBefore/One/Run ChiPengMingGang（己方+OtherSide 三态）, IOnAnGang, IOnJiaGang, IOnOtherSideAnGang/JiaGang |
  | 听牌 | IOnTing, IOnOtherSideTing, IOnProcessTingResultOutput, IOnStartTingAnimFinished |
  | 和牌 | IOnBeforeHuMySide/OtherSide, IOnAboutToHuMySide/OtherSide, IOnHu, IOnHuFinished, IOnAfterChiPengMingGangHu, IOnOtherSideHu, **IGetHuPaiSlotsCount**, IOnHuSlotCountUpdate |
  | 计分 | IOnJiFen, IOnPreviewJiFen(结算预览), IOnOtherSideJiFen(OrPlaying), IOnJiFenFinished, IOnHuAlterPostBoard |
  | 经济 | IOnAddCoin, IOnCoinChanged, IOnOtherSideAddCoin, IGetCoinRatio |
  | 运气 | IOnHaoYun, IOnEYun, IOnZhongYun |
  | 局内其他 | IOnBuffValueChanged, IOnUseSkill, IOnOtherSideActiveSkillTriggered, IOnBaoLingAttach, IRuntimeUpdatable, IGetDynamicDescription(Paras)（动态描述） |
  | 局外/特殊 | IOnMaJiangRoundStart/End, IOnBackToMap(Win), IOnXiaoChouInitApply, IOnXiaoChouChanged, IXiaoChouPaiDestroy, IOnOfferingUsing/Remove/CancelUse, ICanHatchItem, IReviveItem/IConditionReviveItem(复活), IPlayFlySoul, **IAIStartSwapWeight**(改 AI 权重！) |

- **配额管理**：`GvLingyongSlotNum / lingYongNumLimit / GvLingyongRepositorySlotNum / lingYongRepositoryNumLimit`（在场槽＋仓库槽）；`XiaoChouPaiBlackList`（商店不可刷）、`BeginnerList`（新手池）、`NeedUnlockedList`（解锁池）三个 ScriptableObject 做内容门控。

### 3.2 宝牌（Relic，159 类）

局外永久遗物（`RelicId` 枚举驱动），`OutsideGameAction.OnBefore/Add/AfterAddRelicEvent` 三段式入场钩子（先于获得→获得→获得后），与我们远征层"宝物"设计同构。

### 3.3 祭品（Offering，56 类）

对弈内消耗品/挂件（`GvOfferingSlotNum` 槽位），`OnSellOffering / OnOfferingUse / OnCreateNewOffering / OnOfferingCancelUse` 全生命周期钩子。教学文案："你的牌被变成迷幻牌了呀？"——**祭品可污染牌面**（迷幻牌=被修改的牌）。

### 3.4 宝灵（BaoLing / 牌灵）

附着在**具体牌面上**的效果（`BaoLingOutInfo`、`NeedApplyBaoLingDisplays: Dictionary<PaiMianDisplay, BaoLingOutInfo>` 在换牌/和牌/计分各环节被应用）——"给某张牌挂效果"这一层，DLC 专门扩（`MaJiang/DLC/宝牌牌灵DLC表`）。有独立 69 类的 `BaoLingPipe`（管线）＋伪造层 `BaoLingFake` 31 类。

### 3.5 角色与技能

- 玩家角色：**1 主动 + 1 被动**（`MaJiang.PlayMaJiang.Player.Skills.Active` 21 类 / `Passive` 42 类）。主动耗**魂力**（`ISoul.SoulCost`，`GvSoul/SoulMax/SoulRestore/soulRestoreParam`，"每局麻将开始时会自动回复一些魂力"）。
- Boss：`AIBase { characterID, roleAvatar, targetScore, baseScore, independent, greedyConfig, SkillPayloads[], RandomXiaoChouPool×4 }`；Boss 技能有面板（`BossSkillPanel`）与拦截位（`IBossCaskSkill` 插在计分链上）。

### 3.6 AI（贪心权重人格，非搜索）

`GreedyConfig` 全字段（每个 Boss 一份，"AI 总表" ScriptableObject 配置）：

- **逐牌权重**：`_1W.._9W`（万 1-9）、`dongW/nanW/xiW/beiW`、`zhongW/faW/baiW`——AI 想要什么牌，逐张配。
- **结构权重**：`same2/3/4Weight`（对/刻/杠）、`diff1/diff2Weight`（间隔 1/2 的搭子——邻近组合权重）。
- **花色权重**：`wanWeight/tongWeight/suoWeight/fengWeight/sanyuanWeight`。
- **行为权重**：`AIChiW/AIPengW/AIMingGangW/AIAnGangW`（吃/碰/明杠/暗杠倾向）、`jiaGang`、`isOnlyChiPengOpen`、`aiChiPengTypeWan...`（只对特定花色开吃碰）。
- **节奏控制**：`needDelayTing + delayTing/delayMin/delayMax`（延迟听牌）、`needCheckTingFanZhongPeng + checkTingFanZhongList`（按番种限制听牌方向）。
- 决策入口：`AIPipeline.StartSwapWeight(canFetchPaiMianCount, GreedyConfig, ...)`；小丑可经 `IAIStartSwapWeight` 改写 AI 权重（反过来影响对手行为的效果）。
- **无博弈树搜索、无 MCTS**——纯手工贪心评估＋数据配置人格。**这是"验证构筑的对手"的廉价正确解**。

### 4.3 参数系统（三层）

1. **Gv\* 值类**（`MaJiang.ValueClasses`，每参数一个类，SimpleDataInt/Float/IntHasLimit 基类）：GvHp/GvHpMax、GvSoul 族、GvDrawCount（摸牌数）、GvSwapCount（换牌数）、GvTotalDrawCount（总摸牌数）、GvHuSlotCount（和牌槽）、GvPlayerBaseScore（底分）、GvShopPriceMulti、GvInGameCoinsMulti/OutGame…——**这是效果系统的"可寻址参数"**，小丑效果改的是这些具名槽，事件字符串里"参数/生命参数/番数参数…"就是它们（效果节点按名寻址改参数）。
2. **GameConfig**（ScriptableObject，一局对弈全量初始值）：hp/hpMax、soul 族、shop 价、swapPaiRoundTotal/swapPaiTurnTotal/initSwapPaiTotal、huPaiSlotsCount(+软硬上限)、baseScore、coin、乘区、paiMianBaseScore、灵俑/祭品槽上限、discardContainerLength 等 40+ 字段。
3. **Level/AIBase/DifficultyPayload**：按关卡/Boss/难度覆盖。

### 4.4 管线架构（对弈层骨架）

```
BasePipeline (abstract, MonoBehaviour)
 ├─ 持有：牌山容器 · 弃牌容器 · 手牌容器 · 显示(副露)容器 · PlayingContainer
 │        ScoreBoard · HuPaiSlots · BuffList · Soul · 小丑容器 · 番种Payload表
 ├─ OtherSidePipeline 属性 —— 双管线互链，一切 OnOtherSide* 钩子的来源
 ├─ PlayerPipeline（玩家侧，还兼回合驱动——PlayerHandPaiMianContainer 持 TurnPhase）
 └─ AIPipeline（AI 侧，每个钩子签名是 (Input, Output) 元组，决策发生在钩子内）
```

- **驱动方式**：Unity MonoBehaviour 协程/UniTask 串联（`IEnumerable<IPromise> Init()`、`UniTask<OnHuOutput> OnHu(...)`），回合推进与动画强耦合（`DelayAnimations` 队列内嵌在计分 DTO 里）。**没有独立于表现的纯逻辑核**——规则与演出在管线里交织，测试性靠 Decimal 精确结算与种子（gameSeed/battleSeed/randomSeed 全程可复现）保证。
- **事件流**：所有内容（小丑/宝牌/祭品/宝灵/Buff/技能）都通过 90 接口族挂进管线时点；DTO 进、DTO 出，管线按序 reduce。

## 5. 对我们游戏（forbidden-gamble / 真气语法 v3）的开发启示

> 以下是分析结论，不是拍板。哪些采纳由你定；采纳项动代码前照旧先入文档。

### 5.1 直接可借鉴的架构决策（与我们既有方向高度吻合或直接补强）

1. **规则核心独立成模块**：他们把全部逻辑放进 MaJiang.dll、表现层近空。我们计划 `core/mahjong/` 独立模块＝同构，方向被验证。
2. **内容＝钩子实现类＋DTO 协议**：功法/心法不该是数据表解释器一种形态——**效果复杂度上来后，"每张功法一个类＋按需实现钩子"比"数据+解释器"表达力强得多**（他们 470+ 内容类证明可扩展）。我们 v2.2 的 techniques.json+TechniqueResolver 是数据驱动路线，v3 功法挂"式"事件（发射/被截/和牌/计分）时，可以认真评估 **GDScript 版钩子接口**（Godot 无接口，用基类虚方法或 Callable 注册皆可）。这正是 R3 阶段的架构题。
3. **Input/Output DTO 层**：所有钩子数据进出走独立命名空间的 DTO（他们 125 个类专门干这个）。我们的 EffectPipeline 已有 GameAction 概念，方向一致，可加强"每个钩子一对 DTO"的纪律，好处是**快照/回放/测试全免费**。
4. **Gv\* 具名参数注册表**：效果系统需要一个"可寻址参数"层（参数/生命参数/番数参数…），效果按名改参。我们的 DojoConfig/战斗参数可朝这个形态收敛。
5. **AI＝贪心权重配置**：GreedyConfig 的字段设计（逐牌权重＋搭子 diff 权重＋花色权重＋吃碰杠行为权重＋延迟听牌）**几乎可以平移**成我们敌方 AI 的第一版：GDScript 里一个 Resource 配置＋一个贪心评估器，每个敌人一个人格。无须搜索。
6. **Decimal 精确结算＋全程种子**：计分类游戏防浮点漂移＋可复现（他们的 FinalStatistics 连 gameSeed/battleSeed 都记录）。我们 GDScript 用 int 就行，但"全程种子进结算记录"值得抄。

### 5.2 规则设计上值得注意的解法（对照我们 v3）

| 他们的解法 | 我们 v3 对应 | 备注 |
|---|---|---|
| **和牌＝计分事件，不终局**；和牌槽限次数 | 我们是"打空气血"，式/功法是攻击 | 他们保住了"麻将完整性"（听牌/和牌体验完整）同时让单局有肉鸽时长；我们把面子改成弹药、和牌概念退役。**两条路线都成立**，但注意：他们的玩家"想和牌"的动机链完整（番种追求→倍率成长），我们的"想凑式"动机链要靠功法配方强度撑——功法池的深度就是我们版"番种表"的深度 |
| 听牌＝**主动选择**＋锁死＋自动打出＋快进按钮 | v3 无听牌 | 他们用听牌制造"承诺-等待"张力；我们对应物是蓄力功法（承诺-延迟）。他们的"自动打出＋加速"是承认等待无聊的补丁——我们蓄力拍数设计时要防同样的坑 |
| 摸 N 换 N（GvDrawCount/GvSwapCount 分开）＋初始调度 | 摸3弃3 | 同型；他们把"每回合换牌数"和"总摸牌预算"分成两个参数，值得照抄成 v3 的参数位 |
| 共享牌山＋顶/底/随机插牌 API | 气海+气河循环 | 他们牌山可被内容干预（宝牌塞牌）；我们的气河若只做"洗回"就浪费了一个构筑面 |
| 换牌余量独立记账（SwapPaiLeftCount） | — | 换牌次数本身成了资源位，小丑可加减——低成本高杠杆的参数化 |
| 双向吃碰杠窗口＋加杠/暗杠独立时相 | 截者接续、碰杠免费 | 完全一致的拍板，互相印证 |
| 运气事件（好运/厄运/中运→倍率） | — | 把"随机性"包装成可挂钩事件而非裸随机，构筑有抓手 |
| 牌面谓词层（PaiMianType：小/中/大数、幺九、任意） | 数值=结构身份 | 他们把"哪些牌"抽象成枚举谓词，效果描述全部走谓词——我们 v3 的"式"符号之外，**功法查询牌面的谓词层**（如"大数牌"）值得预留 |
| 敌方同核（AIBase 与玩家同管线，仅 GreedyConfig 人格差异） | 敌方同构 | 同拍板，且证明"同核＋权重人格"够撑内容量 |

### 5.3 反面教训（他们踩的坑）

1. **规则与演出同层**：管线是 MonoBehaviour，回合推进嵌动画协程，无法脱离 Unity 跑纯逻辑测试。我们 `core/battle` 纯逻辑+GUT 的路线要守住——**别让演出进核心**。
2. **内容类爆炸无数据化护栏**：470+ 小丑每张一个类，动态描述（IGetDynamicDescription）要单独实现——数值平衡与文本一致性全靠人肉。我们若走类路线，配套"数据卡＋效果类"两层（数值进资源、逻辑进类）。
3. **听牌后纯等待**：靠快进按钮打补丁——规则性的无聊不要用 UI 补。

### 5.4 与我们 R0-R5 实施计划的对接

- **R0（供体核对）**：本报告即"我地麻标本"的产出；GitHub 供体（fastmaj/esrrhs 等）照计划另跑。本游戏**不可作代码供体**（商业闭源），只作设计参照。
- **R1（规则核移植）**：牌表示（struct+谓词枚举）、InRoundTurn 状态机形态、AllPaiMianContainer 的山 API（顶/底/随机插牌）三者都有现成参照。
- **R3（功法层）**：钩子接口族＋DTO 协议是本报告给 R3 的最大输入——功法=实现若干"式事件钩子"的类，攻击/防御/词条差异＝挂不同时点。
- **R4（敌方 AI）**：GreedyConfig 字段表（§3.6）可直接翻译成我们的人格配置 schema。
